# 🎯 双平台战略定位（2026-08-12 确立）

> 来源：用户战略思考。核心：GitHub=营销宣发地，小红书=产品验证地。

## 平台本质认知（为什么GitHub行、RedSkill不行）

```
GitHub = 原生代码交付（raw code delivery）
  - 交付"原材料"（代码/方法/文档）
  - 不审核（开发者自己判断风险）
  - 读者=开发者（能自己加工使用）

RedSkill = 验收产品交付（acceptance-tested product delivery）
  - 交付"成品"（开箱即用的Skill）
  - 严格审核（平台对普通用户负责）
  - 读者=普通人（装了就希望能用）

本质：GitHub接受"知识"，RedSkill只接受"产品"
```

## 双引擎打法（确立）

```
GitHub（全球营销宣发地）：
  - 海外开发者可见，全球影响力
  - 技术背书（代码都在=可信）
  - 免费/无限/不审核
  - 放：方法论/代码/完整Skill源码（原材料）

小红书（产品验证地）：
  - 国内普通人用户，真实市场反馈
  - 验证"这个Skill对普通人有价值吗"
  - 审核严格=逼我们做"真产品"
  - 放：开箱即用/不依赖外部API/装了就有效的产品级Skill

闭环：GitHub宣发（让人知道）→ 小红书验证（看有没有人用）→ 反馈回流（迭代）
```

## 内容→工作流原则

```
所有内容都可以做成工作流？——要看类型：
  ✅ 重复性内容 → 必须做（封面/播客/文章发布）
  ✅ 方法型内容 → 适合（学习法/写作法→Skill）
  ❌ 一次性决策 → 不做（做完就完）

判断标准：这个事会重复做吗？
  会 → 做成工作流（沉淀成Skill/流程）
  不会 → 不留（做完即弃）
```

## 落地

- 以后新Skill：先判断"原材料型"还是"产品型"
  - 原材料型 → GitHub
  - 产品型（开箱即用）→ RedSkill
- cover-pipeline：原材料型 → 留GitHub（不再硬试RedSkill）
- 以后做产品级Skill（不依赖外部API）→ 再上RedSkill
