## 一、v0.3.41：修了两个比配额更致命的缺陷

### 1.1 进度倒退（致命，每天都在发生）

**现象**：KV 配额打满 → 云端写入失败、停在旧版本 → 用户下次打开 App →
**本地新进度被云端旧数据覆盖** → 覆盖结果又被写回云端 → 真进度永久丢失，用户全程无感。

**根因**：`S._ts` 只在「上云副本」上打时间戳，本地那份**从来不更新**，恒为初始值。
而 `pullProfile` 的判定是「云端 `_ts` > 本地 `_ts` 才覆盖」——本地 `_ts` 恒旧，
于是**每次启动都会被云端覆盖**。平时云端是最新的所以看不出问题；
一旦云端写入失败停在旧版本，倒退就发生了。

```js
// 修复前（1208 行）：只给上云副本打时间戳，本地 S._ts 不动
const cloudState = Object.assign({}, S, { _ts: Date.now() });

// 修复后（1193 行）：落盘前先更新本地 _ts，让它真正代表本地进度的新旧
function saveState(){ S._ts = Date.now(); saveStateLocal(); pushProfileSoon(); }
```

**配套修复（顺序不能反）**：启动时原本无条件 `saveState()`，会把 `_ts` 抢先推到 now，
导致多设备场景下判定「本地比云端新」，把本设备旧进度写回云端、冲掉另一台设备的新进度。
改为启动只落本地（`saveStateLocal()`），同步交给 `pullProfile` 合并完成后再触发。

### 1.2 静默失败（严重）

- `pushProfile` 里 `await fetch(...)` **从不检查响应**。worker 返回
  `{"ok":false,"error":"KV put() limit exceeded for the day."}` 前端完全不知道，
  用户以为进度已上云，换设备才发现是空的。
- `sendBeacon` 被用作**常态**路径（不只 pagehide），而 beacon 拿不到响应，
  等于把「永不感知失败」写死在代码里。

改为：常态走 fetch 并检查响应，失败写 `sinoky_cloud_dirty` 标记 + `console.warn` 留痕，
成功则清除标记；sendBeacon 只在 `flushProfileNow`（页面卸载）时使用。

### 1.3 验收

| 层 | 结果 |
|---|---|
| worker 单测 | 7/7（v0.3.40 用例无回归） |
| 浏览器 e2e | **20/20**（含 5 条倒退专项） |
| 生产版本三处 | 0.3.41（部署时 token 被 CF 限流锁定，见 §五） |

e2e 第 8 组是本轮核心：

| 用例 | 场景 | 结果 |
|---|---|---|
| 8A | 本地新 + 云端旧 → 本地不被冲掉 | PASS（修复前会被冲掉） |
| 8B | 同上 → 本地新进度被推回云端（自愈） | PASS |
| 8C | 本地旧 + 云端新 → 本地被覆盖（多设备同步） | PASS（防倒退没误伤同步） |
| 8D | 同步失败 → 写 dirty 标记 | PASS（修复前完全无感） |
| 8E | 同步恢复 → dirty 清除 | PASS |

> **踩坑记录**：8A/8B 最初就是 PASS，但那是**假阳性** —— `page.route` 拦不住
> Service Worker 内的 fetch，GET `/api/profile` 穿透到本地静态服务器拿了 404 的 `"nf"`，
> `pullProfile` 在 catch 里静默吞掉，于是「从来没被覆盖过」自然「没被冲掉」。
> 改用**自建 server 提供 API mock + `serviceWorkers: 'block'`** 后才真正测到。
> （项目已知坑，记忆 §四.1，写新测试时未复用，代价是两轮排查。）

## 二、不上 Workers 付费的真实坏处（按严重度排序）

事实基础（Cloudflare 官方定价，2026-09-03 核实）：

| | 免费档 | 付费 $5/月 |
|---|---|---|
| KV 写入 | **1,000 / 天（账户级）** | 100 万 / 月（≈3.3 万/天） |
| KV 读取 | 10 万 / 天 | 1000 万 / 月 |
| Workers 请求 | 10 万 / 天（账户级） | 1000 万 / 月 |
| 超限行为 | **硬失败，直接报错** | 软的，超额按量计费 |

### 坏处 1：静默失败 → 用户信任崩塌（已缓解，未消除）

v0.3.41 后数据不会倒退了，但**写入失败这件事本身还在**，且用户侧无任何提示。
用户换手机时发现进度少了 —— 这是最伤信任的时刻，比功能缺失严重得多。

**残留风险**：清缓存 / 换设备场景无法自救（localStorage 没了，dirty 标记也没了）。
v0.3.41 只救了「同设备 + 配额满」这个主场景。

> 建议（未做）：在某个二级位置（关于/版本号旁边）显示一行
> 「云端备份：已同步 / 待同步（本地已保存）」。属 Edify Gate 的 🟡 防流失类，
> 不占主路径，但把不可见风险变成可见状态。

### 坏处 2：额度是**账户级**共享，不是 Sinoky 独占

1,000 写/天是**整个 CF 账户所有 Worker 脚本**共享的（官方原文 "Across all of your Worker scripts"）。
你的 `/api/feedback` 也写 KV —— **反馈功能和进度同步在同一个池子里抢额度**。
意味着：反馈被刷（或用户爱用）→ 进度同步先挂。一个功能的用量拖垮另一个功能。

### 坏处 3：硬闸门 —— 超限是「全天停摆」，不是「变慢」

免费档超了就报错，到 UTC 00:00（**北京时间 08:00**）前**所有写入 100% 失败**。
重置时刻在北京时间早上 8 点，而用户活跃高峰在晚上 ——
**当晚间把额度耗光，整个晚高峰的同步全部失效**，且要等到第二天早上才自愈。

付费档是软的：超了只是多花钱（$5/百万写），不会停摆。这是"硬失败"和"软超额"的本质区别。

### 坏处 4：看板数据有缺口 → 可能让你做错产品决策（隐性成本）

`recordStat` 入库也走 KV 写。配额满的那几个小时，`featDist`（功能使用分布）数据不入库。
你正打算靠 featDist 决定「cards 要不要扩充」——
**如果缺口恰好落在活跃高峰，你看到的分布是偏的，据此做的决策也会偏**。

这条不花钱，但可能让你在错误的方向上投入。是最容易被忽略的坏处。

### 坏处 5：架构被锁死在「低频、可丢失、可本地兜底」

你现在能做的写入，必须满足：低频 + 丢了不致命 + 本地能兜底。
**以下功能在免费档下做不了**（全是高频写）：

- 用户生成内容（UGC）、评论区、学习笔记同步
- 打卡排行榜、学习 streak 的社交化
- 多人/语伴实时互动（记忆里 L3 语伴互认的方向）
- 任何"每次操作都要落库"的东西

> 你说接下来要规划新思路 —— **这条对新思路的约束力最大**。
> 新方向如果含上面任何一类，免费档会直接堵死，届时不是"花钱"的问题，是"架构要重写"的问题。

### 坏处 6：Workers 请求数也是天花板（比 KV 晚，但别忽略）

10 万请求/天（账户级），包含 TTS / ASR / profile / feedback 全部 API。
按每活跃用户每天 120–165 次 API 请求估算：**约 600–700 活跃用户触顶**。
比 KV 晚，但同样是账户级、同样是硬失败。

## 三、免费档下能做的三条应对（不用花钱）

| 优先级 | 动作 | 收益 | 成本 |
|---|---|---|---|
| A | 同步状态可见（关于页加一行） | 把不可见风险变成可见状态，救信任 | 小 |
| B | feedback 端点改为不写 KV，或合并进 `/api/profile` 一起提交 | 把额度让给进度同步 | 小 |
| C | 看板加「今日 KV 写入量」指标 | 提前看到"快满了"，而不是等它炸 | 小 |

C 的实现注意：计数器本身也消耗写入，用**每 10 次写更新一次计数器**，误差 ≤10 次可接受。

## 四、上付费的真正触发线（建议改）

**不要用用户数当阈值，用日写入量。** 理由：写频取决于「人 × 会话内进度变化次数」，
跟用户数不是线性关系 —— 100 个重度用户可能比 500 个轻度用户更费。

| 触发条件 | 动作 |
|---|---|
| 日写入连续 3 天 > 600（免费档 1000 的 60%） | **上付费**。单日波动就可能触顶 |
| 日 API 请求连续 3 天 > 6 万（10 万的 60%） | **上付费**。Workers 请求也要触顶了 |
| 日写入 < 300 | 安全，继续观察 |

按当前 ~5–15 写/人/天估算（**估算值，待看板实测校正**）：

- 66–200 活跃用户 → KV 写入开始吃紧（**远早于你设的"破千"**）
- 600–700 活跃用户 → Workers 请求触顶

**所以：不是"破千再上"，是"破两百就要盯，破六百必须上"。**
