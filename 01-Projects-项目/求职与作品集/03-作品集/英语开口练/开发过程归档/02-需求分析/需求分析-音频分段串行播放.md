# 02 需求分析 · 音频分段串行播放

**对应需求**：`01-需求调研/需求调研-挑战页音频顺序反馈.md`

## 一、现象
点播放 → 先听到中文"苏不倦"，后听到英文"Hi, my name is"。应为英文先、中文后。

## 二、根因定位
排查链路：`renderDaily` 播放按钮 `onclick="speak(s.en)"` → `speak()` → `splitByLang()` 分段（顺序正确：英文段→中文段→标点段）→ `playNextSeg()` 串行播放。

**关键 bug 在 `playAudioSegment`**（约 2482 行）：
```js
audio.onplaying = () => finish(true);   // ❌ 音频"刚开始播放"就 resolve
audio.onended  = () => {};              // ❌ 真正播完却什么都不做
```
`speak()` 中 `playAudioSegment(url).then(() => playNextSeg())` —— 因为 `onplaying` 在播放**开始**瞬间就 resolve，下一段立刻被 `playNextSeg` 启动，导致**本段未播完、下一段已并发播放**。

在微信 X5 内核里：
- 中文走百度 TTS 源（`gettts?lan=zh`），延迟低、出声快；
- 英文优先走有道 `dictvoice`，常被 X5 拦截/缓慢。

于是并发时中文段先被听到，表现为"顺序反了"。

**为什么不是 `splitByLang` 的锅**：正则 `/([\u4e00-\u9fa5]+)|([^\u4e00-\u9fa5]+)/g` 按原文从左到右切分，段顺序天然正确，无需改。

## 三、方案对比与取舍
| 方案 | 做法 | 优劣 |
|---|---|---|
| A（选） | 改 `onended` 才 resolve 推进下一段；`onplaying` 改空操作 | 改动最小、语义正确、全站分段 TTS 统一受益 |
| B | 预加载全部段再顺序 `play()` | 复杂、且音频源可能超时，收益不大 |

**选 A**。

## 四、验收标准
1. 中英混排句严格串行：英文段 → 中文段 → 标点段，无并发重叠。
2. 单段播放失败（源拦截）时，按源列表 fallback，最终兜底 Web Speech，不影响顺序。
3. 挑战页 / 对话页 / 跟读页所有分段 TTS 表现一致。
