# 01 需求调研 · 跨平台直接打开能力

**调研日期**：2026-08-28 20:25
**调研人**：九思
**诉求来源**：康哥要求 App 在微信内可直接打开运行，兼容抖音、小红书等主流平台打开方式，同时支持电脑端浏览器访问；并明确目标用户规模、性能与稳定性要求。

---

## 一、诉求拆解

| 诉求 | 具体含义 |
|---|---|
| 微信内直接打开 | 微信聊天/朋友圈/公众号/视频号点链接即能跑，不跳外部浏览器也能用 |
| 抖音兼容 | 抖音主页链接、评论区、私信卡片打开可用 |
| 小红书兼容 | 笔记/主页链接打开可用 |
| 电脑端浏览器 | Chrome / Edge / Safari 桌面版直接访问可用 |
| 用户规模指标 | 明确 DAU 或并发量级，作为性能设计依据 |
| 验收条件 | 各平台可量化的通过标准 |

---

## 二、现状勘察（代码层实测）

勘察对象：`english-speaking-app/index.html`（当前线上 `841241a` 版本）

| 项 | 实测结果 | 影响 |
|---|---|---|
| 文件体积 | **686,393 字节（670KB）** | 单文件首屏全量下载，移动网络压力大 |
| 体积构成 | 其中约 **470KB+ 为 base64 内联图片**（微信收款码等） | 非首屏必需内容却阻塞首屏 |
| 外部依赖 | `miaoda.feishu.cn` 字体 CSS（Noto Serif SC / Noto Sans SC 共 7 个字重） | 阻塞渲染的外部请求，国内访问不稳定，且字重过多 |
| 录音调用 | 3 处 `navigator.mediaDevices.getUserMedia({ audio: true })`（第 2740 / 2810 / 3277 行） | 核心功能，平台支持是最大变量 |
| 打分实现 | `window.SpeechRecognition \|\| window.webkitSpeechRecognition` | 依赖浏览器内置语音识别，平台支持差异极大 |
| 平台判断 | 已有 `isWeixin()`（第 2446 行），仅用于失败文案区分 | 尚无完整能力探测与降级体系 |
| viewport | `width=device-width, initial-scale=1.0, maximum-scale=1.0, user-scalable=no` | `user-scalable=no` 在 iOS 10+ 被忽略，且不利无障碍 |
| PWA | 无 manifest、无 apple-mobile-web-app 配置 | 无法"添加到主屏幕"，只能靠链接传播 |

## 三、平台能力调研（关键，含查证来源）

### 3.1 录音能力（getUserMedia + MediaRecorder）

| 环境 | 支持情况 | 关键限制 |
|---|---|---|
| **iOS 微信** | ❌ **不支持** | 使用系统 WKWebView，**不支持媒体设备访问**（RTC 服务商文档明确："无法开播，只能订阅"）；偶发 `NotAllowedError` |
| iOS Safari | ⚠️ iOS 14.3+ 支持 | 需 HTTPS + 用户手势 + 页面前台；老旧 iOS（11.0–14.2）除 Safari 外均不支持 |
| Android 微信（X5 v7.x 及更早） | ❌ 基本不支持 | API 存在但底层未桥接硬件通道 |
| Android 微信（X5 v8.0+） | ⚠️ 实验性支持 | 常返回空 MediaStream、音频静音、无权限弹窗透出机制 |
| Android Chrome | ✅ 支持 | 需 HTTPS + 用户主动交互 + 页面前台 |
| **抖音 / 快手 / 钉钉内嵌 WebView** | ⚠️ 需实测 | 自研 WebView 安全策略，文档记录其"主动移除部分 API"，录音能力存在被屏蔽风险 |
| 小红书内嵌 WebView | ⚠️ 需实测 | 同上，自研内核，无公开能力文档 |
| 桌面 Chrome / Edge | ✅ 完全支持 | 最佳体验环境 |

### 3.2 语音识别打分（SpeechRecognition）

| 环境 | 支持情况 | 说明 |
|---|---|---|
| iOS Safari 17.6+ | ❌ **完全不支持** | WebKit 官方标记 "Not planned"（Bug #170773） |
| **微信 iOS 内置 WebView** | ❌ **强制禁用** | WKWebView 内核阉割 |
| **抖音 / 快手 / 钉钉内嵌 WebView** | ❌ **默认屏蔽或返回空实现** | 自研 WebView 安全策略**主动移除 `window.SpeechRecognition`** |
| Android Chrome 120+ | ✅ 有条件支持 | HTTPS + 用户主动交互 + 页面前台 + 无系统级录音拦截 |
| 桌面 Chrome / Edge | ✅ 支持 | 最佳体验环境 |

### 3.3 查证来源

1. CSDN 问答《微信H5中调用 navigator.mediaDevices.getUserMedia 为何报错或无响应》（2026-03）
2. 腾讯云 RTC 服务商浏览器支持文档（微信浏览器 iOS 标注为"仅订阅"）
3. GitHub `xiangyuecn/Recorder` 兼容性说明（支持 iOS 14.3+、Android X5；不支持老旧 iOS 非 Safari 浏览器）
4. CSDN 问答《JS语音识别在移动端为何常触发失败或无响应》（2026）——含"能力断层图谱"
5. CSDN 问答《内嵌H5中 navigator.mediaDevices.getUserMedia 为何无法访问摄像头/麦克风》（2026-02）

## 四、三大阻断性风险（必须向康哥明示）

### 风险 1：iOS 微信内核心功能不可用（最高优先级）
录音（getUserMedia）与打分（SpeechRecognition）在 iOS 微信内**双双被禁用**。而"录音跟读 + 自动打分"正是本 App 的核心交互。这意味着 **iPhone 用户在微信里打开，核心功能直接失效**。

### 风险 2：抖音 / 小红书内打分功能不可用
两家均为自研 WebView 且主动移除 `window.SpeechRecognition`，打分功能必然失效；录音能力需真机实测确认。

### 风险 3：首屏体积 670KB，移动端弱网体验差
其中 470KB 是收款码等 base64 图片，属非首屏必需内容；外加外部字体请求阻塞渲染。在移动网络下首屏可能 3–8 秒，弱网环境更差，直接影响跳出率。

---

## 五、结论与建议方向

> **不能承诺"微信/抖音/小红书内完整可用"** —— 这是平台内核限制，非代码可解决。可行方向是**能力探测 + 优雅降级 + 引导**：

1. **能力探测**：运行时检测 `getUserMedia` / `MediaRecorder` / `SpeechRecognition` 是否真实可用（不只判断存在性，要实际调用试探）。
2. **降级模式**：能力缺失时自动切换到"只听跟读模式"——保留听标准音、看文本、手动自评（滑动打分），剔除录音与自动打分。
3. **引导外跳**：检测到微信/抖音等受限环境时，提示"在浏览器打开可获得完整体验"，提供复制链接 / 一键跳转按钮。
4. **首屏瘦身**：图片外置或懒加载、字体本地化或异步加载，把首屏压到 200KB 以内。
5. **真机实测**：上述结论基于公开文档，**抖音、小红书必须用真机实测确认**（文档无公开能力说明）。
