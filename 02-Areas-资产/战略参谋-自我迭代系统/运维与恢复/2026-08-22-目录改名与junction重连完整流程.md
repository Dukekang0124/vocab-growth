# 目录改名 + junction 重连完整流程（WorkBuddy 工作空间迁移）

> 2026-08-22 实战验证 · 康哥地盘改名 `08-WorkBuddy知识库` → `08-九思搭档知识库`
> 适用：任何"改目录名 / 迁移含 junction 的目录 / WorkBuddy 工作空间换路径"场景

## 一句话结论

**含 junction 的目录改名，必须"改名 + 重连 junction + 同步路径引用"原子化完成，中间零间隙，否则 WorkBuddy 启动崩溃打不开。**

## 根因（崩溃日志铁证）

WorkBuddy 启动时执行 `ensureWorkbuddyDataDirs`，会 `mkdir C:\Users\Admin\.workbuddy\skills`。
`skills` 是 junction 软链接 → 指向旧目录的 04-SKILL。
只改目录名、不重连 junction → 软链接悬空 → mkdir 报 `ENOENT: no such file or directory, mkdir '...\skills'` → 主进程崩溃。

证据位置：`C:\Users\Admin\.workbuddy\logs\Crash-Log\crash-report-main-*.json`

## 完整流程（5 步，原子化）

1. **杀进程**：`taskkill /F /IM WorkBuddy.exe`（改名必须进程退出，否则目录被锁 Permission denied）
2. **清空壳**：若新目录已存在且为空 → 删除（WorkBuddy 可能按配置自动建了空壳）
3. **改名**：`os.rename(OLD, NEW)`（Python UTF-8 原生支持中文路径）
4. **立即重连 junction**（紧跟改名，零间隙）：删旧链接 → `mklink /J` 新链接
5. **验证**：新目录存在 + junction 能列出技能 + 技能库可访问

## 关键坑（今天踩出来的）

| 坑 | 解法 |
|---|---|
| `os.path.islink()` 对 Windows junction 返回 **False**（只识别 symlink）| 用 ctypes `GetFileAttributesW` 检测 `FILE_ATTRIBUTE_REPARSE_POINT(0x400)` |
| bat 文件写中文（UTF-8）被 cmd 按 GBK 解析成乱码，命令断裂 | bat 纯 ASCII 只做启动器，核心逻辑用 Python（UTF-8 原生中文）|
| 只改目录名，漏了状态文件里的旧路径 | 同步改：app-config / USER.md / MEMORY.md / sessions.json / db sessions.cwd / artifact-index / automation cwds |
| WorkBuddy 按 app-config 自动建空壳新目录挡路 | 改名脚本里自动清空壳（检测非空则中止防丢数据）|
| 历史快照/日志/审计里的旧路径 | **不改**（modify_backup、file-history、logs、audit-log 是历史事实，改了破坏 undo/版本/审计）|

## 可复用 Python 脚本（核心片段）

```python
import ctypes, os, subprocess
FILE_ATTRIBUTE_REPARSE_POINT = 0x400

def is_reparse_point(path):
    attrs = ctypes.windll.kernel32.GetFileAttributesW(path)
    return attrs != 0xFFFFFFFF and bool(attrs & FILE_ATTRIBUTE_REPARSE_POINT)

def remove_junction(path):
    if not os.path.lexists(path):
        return True
    if not is_reparse_point(path):  # 真目录不删，防误删数据
        return False
    for fn in (lambda: os.rmdir(path), lambda: os.unlink(path)):
        try:
            fn(); return True
        except OSError:
            continue
    return subprocess.run(["cmd","/c","rmdir",path]).returncode == 0

def make_junction(link, target):
    return subprocess.run(["cmd","/c","mklink","/J",link,target], capture_output=True).returncode == 0
```

## 残留分类决策（改名后必做，2026-08-22 补充）

改名+重连成功后，全盘扫描仍会残留旧路径（本事件约 408 处）。**不是全改，分两类**：

| 类型 | 数量 | 处理 |
|---|---|---|
| modify_backup 内容快照 | 302 | **不改**：undo 机制的"修改前原稿"，改=篡改 |
| file-history 版本历史 | 89 | **不改**：文件历史版本，改=破坏版本链 |
| logs 日志 | 54 | **不改**：运行日志，历史事实 |
| projects 目录名 | 13 | **不改**：历史项目缓存，编码了旧路径 |
| audit-log 审计 | 2 | **不改**：审计记录，改=造假 |

**判断标准：功能引用（改）+ 历史事实（不改）。**
- 必须改：USER.md、artifact-index、app-config、db、automation、MEMORY、工作空间日志、plans、traces、modify_backup_meta（含 png/bat 后缀的纯文本路径 meta）
- 不该改：任何记录"改名前的真实状态"的快照/日志/审计

**注意坑**：grep 二进制 db 会误报残留（实际已干净），需用 sqlite 精确查；modify_backup_meta 存的是真实文件路径，漏改会导致 undo 功能失效。

## 教训

- 改名前**先查崩溃日志定位根因**，别盲试（今天就是查了 crash-report 才锁定 junction 悬空）。
- 改名/迁移目录，先做"路径引用全盘扫描"，列清单再动手，一个不漏。
