# Skill 的本质：不是提示词，是能力商品

## 核心洞察

做了大量 Skill 之后的深度思考——Skill 不只是「好用的提示词」：

| 传统理解 | 本质理解 |
|---|---|
| Skill = 提示词模板 | Skill = 可复用的**能力商品** |
| 用户需要懂技术 | 用户无关性：用户只管结果 |
| 做好就行 | 需要架构设计（中心型+辐射型）+ 质量维护（像代码一样迭代） |
| 孤立的 | 必须与内容互养：文章→产品→案例→Skill，形成闭环 |

## 关键认知

1. **Skill 是把人的经验外化。** 不是写一段 prompt，是把「你怎么想的、你怎么判断的」封装进去
2. **Skill 的边界会扩大。** 下一步跟 Agent 结合实现自动进化
3. **平台的责任是「能力分发」**，不是简单列表

## 底层机制：渐进式披露

Skill 不是一次性全加载——三层按需机制省 Token：

| 层级 | 什么时候加载 | 加载内容 | Token 消耗 |
|---|---|---|---|
| 第一层 | Agent 启动时 | 所有 Skill 的 name + description | 极低，100 个也不占满 |
| 第二层 | 用户请求匹配时 | 触发对应 Skill 的 skill.md 正文 | 按需 |
| 第三层 | 执行到对应环节时 | reference/scripts/assets | 仅必要环节加载 |

> 所以「装 Skill 会撑爆上下文」是误解。**Skill = 长胖了的 Prompt + 智能按需加载。**

## 跟苏不倦的关系

你已经在做「经验外化」——口播审稿清单、排版 SOP、发布流水线都是这个逻辑。这篇帮你升级认知：从「我会做 Skill」到「我理解 Skill 的本质和价值」。
