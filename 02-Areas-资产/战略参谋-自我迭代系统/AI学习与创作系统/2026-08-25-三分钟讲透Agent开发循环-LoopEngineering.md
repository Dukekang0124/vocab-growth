## 一、核心观点（一句话）

**Agent 写完不要一遍遍人肉检查——先把「完成标准」写死，再让 Agent 自己「开发→检查→修复」循环到达标；单目标跑通后，用「任务队列 + 独立 Agent 复核」批量推进多目标。**

这是从「写 Prompt」到「设计 Loop」的范式升级：完美的 Prompt 只能换来一次好结果，**一个会自我纠错的闭环，才能让 Agent 真的把活干完。**

---

## 二、单个目标的开发循环（最小闭环）

```
写清完成标准（验收条件）
        ↓
让 Agent 自动开发
        ↓
自动检查（跑验证/读错误）
        ↓
不合格 → 自动修复 → 回到「检查」
        ↓
合格 → 达标，结束
```

关键：**「完成标准」是起点，不是终点**。标准要具体到可验证（测试通过、lint 无错、不碰无关模块、输出摘要），否则 Agent 不知道「什么样算干完」。

---

## 三、多目标推进：任务队列 + 独立复核

单个目标跑通后，不能靠人一个个喂。升级做法：

| 机制 | 干什么 | 为什么 |
|:--|:--|:--|
| **任务队列** | 把 N 个目标排成队，Agent 依次自动完成 | 摆脱「人催一步做一步」 |
| **独立 Agent 复核** | 用第二个 Agent 检查第一个 Agent 的产出 | 自己查自己盲区大（同源偏见） |

这对应搜索结果里「Loop Engineering」的标准动作：**Read → Decide → Act → Verify → Record** 六步法，循环回到状态机上，每轮观察结果回写，成为下一轮 Prompt 的一部分。

## 五、可落地的一条动作（本周可试）

给九思/任何 Agent 下任务时，补一行「验收标准」：

> 任务：写口播脚本「XXX」
> 验收标准：①开头2秒有反常识钩；②含可收藏抓手；③结尾有结果承诺；④能过 36+2 维；⑤不出现「学任何东西都适用」类升格段。

达标才算「完成」，不达标自动改到达标——这就是这篇笔记说的「先写清完成标准，再让它自动开发、检查、修复，直到达标」。
