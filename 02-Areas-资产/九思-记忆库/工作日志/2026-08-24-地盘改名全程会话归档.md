## 二、问题与解决方案（核心决策记录）

### 2.1 根因（崩溃日志铁证）
- 崩溃日志：`ENOENT: no such file or directory, mkdir 'C:\Users\Admin\.workbuddy\skills'`
- 机制：WorkBuddy 启动时 `ensureWorkbuddyDataDirs` 会 mkdir skills 目录；skills 是 junction 指向旧路径，改名后旧路径消失 → junction 悬空 → mkdir 失败 → 主进程崩溃
- **结论：手动改名后必须立即重连 junction，改名+重连必须原子化（零间隙）**

### 2.2 解决方案（原子化脚本）
- taskkill 杀 WorkBuddy 进程 → 清空壳 → `os.rename` 改名 → ctypes 检测+删旧 junction → `mklink /J` 重连 → 验证
- 启动器 bat 纯 ASCII（防中文乱码），核心逻辑用 Python（UTF-8 原生支持中文路径）

### 2.3 全量路径替换（560+ 处）

## 四、核心坑（勿重踩）

1. **改名+重连 junction 必须原子化**，中间零间隙，否则 ENOENT 崩溃
2. **`os.path.islink()` 对 Windows junction 返回 False**（只识别 symlink）→ 必须 ctypes `GetFileAttributesW` 查 `FILE_ATTRIBUTE_REPARSE_POINT(0x400)`
3. **bat 写中文（UTF-8）被 cmd 按 GBK 解析成乱码** → bat 纯 ASCII 启动器 + Python 核心逻辑
4. **grep 二进制 db 会误报残留**（db 实际已干净，需用 sqlite 精确查）
5. **modify_backup_meta 里存真实文件路径**，改名后需同步，否则 undo 功能失效
